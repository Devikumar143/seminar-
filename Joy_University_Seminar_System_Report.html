2 Problem > Solution

The Traditional Problem
  • Paper passes easily lost, forgotten, or shared.
  • Slow manual paper sign-in queues causing congestion.
  • Fake, forged, or unverified participation certificates.
  • Overbooked seminar halls beyond fire code safety limits.
  • No automated waitlists when registered students don't show.
➔
JoySeminar Fixes
  • Single-use cryptographic QR passes rendered on mobile.
  • Sub-second device camera QR scanner at venue doors.
  • Tamper-proof PDF certificates with live public hash verify.
  • Strict concurrency locking preventing overbooking.
  • Automated FIFO waitlist promotion upon cancellations.

2 Data & Storage Architecture

PostgreSQL Relational Storage
  • Normalized 3NF relational schema in `seminar_system_db`.
  • Transactional row-level locking (`SELECT ... FOR UPDATE`).
  • Foreign key cascades on registrations, attendance & waitlist.
  • Indexed lookups on `qr_code_token`, `certificate_id` & emails.
Stateless JWT & Client Caching
  • Cryptographically signed Bearer JWTs with 7-day expiration.
  • React Context state for live user session & notifications.
  • Client-side localStorage pass caching for offline viewing.
  • Axios HTTP interceptors with auto-token injection.

PAGE 5 / 6 Algorithm & Security Logic

1 QR Verification & Attendance Pipeline

PROCEDURE ScanAndMarkAttendance(qrToken, seminarId, adminUser): BEGIN TRANSACTION // 1. Lookup registration by cryptographic token reg = SELECT * FROM registrations WHERE qr_code_token = qrToken FOR UPDATE; IF reg IS NULL THEN ROLLBACK; RETURN REJECT("Invalid or Unrecognized QR Pass"); IF reg.status != 'confirmed' THEN ROLLBACK; RETURN REJECT("Pass is not confirmed"); IF reg.seminar_id != seminarId THEN ROLLBACK; RETURN REJECT("Pass belongs to another seminar"); // 2. Check for duplicate scan collision att = SELECT * FROM attendance WHERE registration_id = reg.id; IF att EXISTS THEN ROLLBACK; RETURN REJECT("ALREADY CHECKED IN at " + att.check_in_time); // 3. Record attendance & release transaction INSERT INTO attendance(registration_id, check_in_time, status, marked_by) VALUES (reg.id, CURRENT_TIMESTAMP, 'present', adminUser.id); COMMIT; // 4. Dispatch notification & activate certificate eligibility TriggerCertificateGeneration(reg.id); SendConfirmationAlert(reg.user_id, "Attendance Verified"); RETURN SUCCESS("Check-in Confirmed: Welcome " + reg.student_name); END PROCEDURE
How it Works
The camera scan decodes the encrypted token string. A 4-layer validation pipeline checks token authenticity, active status, seminar scope, and duplicate guards in sub-100ms.
FIFO Waitlist Promotion
When a cancellation occurs, the engine locks the waitlist with FOR UPDATE, fetches the student at position 1, generates their pass, and notifies them via email automatically.
Inputs & Security State
Inputs: qr_code_token, seminar_id, admin_id. State: ACID compliant PostgreSQL relational commit.

2 6 Critical Security Checks & Conflict Resolvers

1. Duplicate Scan Guard
Prevents pass-sharing among students. Re-scans return previous timestamp.
2. Cross-Seminar Collision
Prevents a pass for Seminar A from being accepted at Seminar B's entrance.
3. Over-Capacity Race Condition
Row-level locking (`FOR UPDATE`) halts registrations once capacity hits 0.
4. Tamper-Proof Certificate Hash
Unique hash token prevents forging or photoshopping certificates.
5. Waitlist Queue Starvation
Ordered promotion guarantees first-come first-served queue fairness.
6. RBAC Privilege Escalation
JWT role middleware blocks unauthorized students from scanner endpoints.
